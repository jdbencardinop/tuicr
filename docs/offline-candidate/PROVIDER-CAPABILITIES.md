# Provider capability limitations — offline-candidate build

Source of truth: `src/forge/capabilities.rs` (evidence-backed capability
profiles) and the research workspace's
`docs/findings/providers/provider-semantics.md`. This file is a condensed
summary generated by hand from that source at packaging time; if it and the
source disagree, the source wins.

| Provider | Diff model | Sides | Range | Create thread | Pending review | Request changes | Reply | Thread resolution | Live-validated? |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| GitHub | Unified | single-side | same-side | Native | incremental | Native | Native | Thread (GraphQL) | Reads: yes (prior evaluation). Writes: offline/fixture only in this archive. |
| GitLab | Version-pair | single-side | same-side | Native | Unsupported (no verified public object) | Emulated via `mergeRequestRequestChanges` (per-reviewer state, not review-level) | Native | Discussion | Reads: yes (prior evaluation). Writes: offline/fixture only in this archive. |
| Azure DevOps | Iteration-pair | simultaneous both sides | dual-side offsets | Native | Unsupported | Vote-based | Native | Thread | Live create/reply/status, native-anchor/TUI stale handling, and non-draft approve/suggestions/wait/reject/reset pass. |
| Gitea (1.24.7 pin) | Unified | single-side | **None** (silently drops `extra_lines_count` rather than rejecting) | **Unsupported** | single-shot only | Native | **Unsupported** | **None** | Offline against a disposable local Gitea 1.24 instance. |
| Forgejo (16.0.1 pin) | Unified | single-side | same-side | **Unsupported** | incremental | Native | **Unsupported** | **None** | Offline against a disposable local Forgejo 16 instance. |

Key limitations to know before relying on this build:

- **Gitea/Forgejo never support standalone thread creation, reply, or
  resolve** on the evidenced pins above. The tool reports these operations
  as `Unsupported` (both in `tuicr review publish --dry-run` planning and at
  real execution time) — it does not silently drop them or pretend they
  succeeded. If you need those operations, they are a genuine capability
  gap in Gitea/Forgejo's REST APIs on these versions, not a bug in this
  fork.
- **No provider models a create-idempotency key.** Every profile's
  `create_idempotency` is `false` — retrying a publish after a failure can
  create duplicate remote comments/threads. The client is responsible for
  persisting an operation ID and reconciling before retrying; this build
  does not yet do that automatically.
- **Azure DevOps pagination is mixed, not uniform**: PR/iteration/change
  lists use `$top`/`$skip`, but commit lists use an opaque continuation
  token. Gitea/Forgejo/GitHub/GitLab pagination is uniform page-number
  style.
- **GitLab has no review-level "request changes" state** like GitHub's.
  This build emulates it by calling the real `mergeRequestRequestChanges`
  GraphQL mutation against the *calling user's own* per-reviewer review
  state — narrower than GitHub, and requires the caller to already be an
  assigned reviewer.
- **Version bucketing for Gitea/Forgejo**: Gitea buckets on `major.minor`
  (only the `1.24.x` line is evidenced); Forgejo buckets on `major` only.
  Passing an unevidenced version falls back to this codebase's single
  evidence-backed default for that provider rather than guessing.

## What "live-validated" means here

"Reads: yes (prior evaluation)" means an earlier phase of this project's
evaluation work performed real GitHub/GitLab reads against disposable
targets (see `docs/findings/providers/smoke-tests.md` in the research
workspace) — not that this specific packaged archive performed a live call.
Producing this archive did not perform any external network write. Treat
every provider row as offline-verified for the purpose of this specific
build; live mutation validation remains a tracked, separate evidence gap
(`docs/follow-on-map/tickets/04-provision-provider-sandboxes.md`).
